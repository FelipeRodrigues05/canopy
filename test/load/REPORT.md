## Methodology

- Closed loop: 64 virtual clients, each sends its next request as soon as the previous one answers, for 30s per HTTP scenario. Latency is measured client side (through nginx, including TLS-free HTTP, auth and the full SQL transaction).
- Request mix: 80% `BET 1.00`, 15% `WIN 1.50`, 5% idempotent replays of an earlier request (same key and body).
- Bearer token from Keycloak (`provider-a`, client credentials); every request is authenticated.
- `distributed`: 500 wallets; `hot-wallet`: 3 wallet(s), so most requests queue for the same row lock.
- `sqs`: 3000 `WagerTransactionRequested` messages (one FIFO group per wallet) sent in batches, timed until the queue is empty (visible + in flight).
- Counters come from `/metrics` of each replica (before/after deltas, summed); `outbox_lag_seconds` sampled every 500 ms.
- Afterwards every wallet is reconciled through `POST /wallets/:id/reconciliation`.

## Analysis

### 1. Correctness held under load

- **0 errors** (5xx or network) and **0 inconsistent wallets** out of 503 reconciled.
- The counters add up exactly: `wager_transactions_total` = requests − replays (distributed 4505 − 217 = 4288; hot wallet 2831 − 128 = 2703). Every replay was recognised as a duplicate and none created a second transaction.
- Each applied transaction produced its two events (`WagerTransactionProcessed` + `WalletBalanceChanged`); the SQS run gives the cleanest check: 3000 messages → 3000 transactions → 6000 events published.
- No message went to the DLQ, and no transaction retry was needed.

### 2. Where the time goes: CPU in the application, mostly in the ORM

Each replica sat at ~100% of one core (Bun runs JavaScript on one thread) while Postgres used ~1.8 of 12 cores. The service is **CPU-bound in the application**, not in the database.

A CPU profile of one replica under load (`bun --cpu-prof-md`, 15 s, 32 clients) attributes the self time like this:

| Where | Self CPU |
|---|---|
| MikroORM (`@mikro-orm/core` + `@mikro-orm/sql`) | **37.7%** (plus much of the 36% "native" time it calls: `freeze`, `cloneObject`, `filter`...) |
| `pg` driver | 2.3% |
| HTTP stack (Express/Nest/router) | ~3% |
| Canopy's own code | 1.5% |
| `jose` (JWT verification), `decimal.js` | 0.6% each |

Query **building** dominates: `QueryBuilder.toQuery` alone is 11% inclusive, and MikroORM formats each statement client side (`formatQuery`, `escapeLiteral`). A submission runs about ten statements, so ORM overhead multiplies.

Single-client latency, for reference: `GET /health/live` 0.5 ms, authenticated `GET /wallets/:id` 2.9 ms, `POST` BET 17 ms, of which ~6.5 ms is the `fsync` on commit (measured by turning `synchronous_commit` off temporarily).

### 3. Hot wallet: correctness bought with queueing

With 64 clients on 3 wallets, every submission for a wallet waits for that wallet's row lock (`SELECT ... FOR UPDATE`). The result is what the design predicts:

- **no lost update, no negative balance, no lock conflict and no retry**: pessimistic locks make transactions wait in line instead of failing and retrying;
- **the cost is tail latency**: p99 ~3 s, against ~1.4 s in the distributed run. Throughput per wallet is about 30 transactions/s, bounded by how long the lock is held (round trips and the commit `fsync`).

`lock_conflicts_total` counts deadlocks, serialization failures, lock timeouts and lost insert races; ordinary lock **waiting** does not show there. It shows up in `wager_processing_duration_seconds`.

### 4. Messaging

- **Outbox lag** stayed under 1.5 s while the API was saturated, and was 0 two seconds after the load stopped.
- **SQS**: 3000 messages drained in ~40 s (75–80 msg/s) by three consumers, with messages of each wallet (FIFO group) processed in order. The same CPU limit applies; the consumers also share each replica's single thread with the API and the workers.

### 5. A real bug the load test found

The first full run had **one 502** out of 5721 requests. Cause: the app's HTTP server closed idle keep-alive connections after 5 s (the Node/Bun default) while nginx kept them pooled for longer, so nginx occasionally reused a connection the app had just closed. The same would happen behind an AWS ALB (60 s idle timeout). Fixed in `src/main.ts` (`keepAliveTimeout` 65 s, above any balancer), and the next full run had 0 errors.

### 6. Variance and honesty

Everything ran on one laptop that was also running a desktop session and a browser. Two full runs of the same configuration gave **190 vs 149 req/s** (distributed) and **75 vs 92 req/s** (hot wallet). The tables above are the latest run; treat the absolute numbers as a lower bound, and the shape (distributed vs hot wallet, p99 growth, zero errors and zero inconsistencies) as the result.

### 7. What I would do next, in order of expected gain

1. **Hot path in parameterized SQL** (`em.execute` with `$1..$n`) for the ~10 statements of a submission, keeping MikroORM for everything else. The profile says this is where the CPU goes.
2. **Fewer round trips**: `lock_timeout` as a role setting instead of `SET LOCAL` per transaction; skip the pre-lock idempotency lookup for first-time requests; one CTE for the transaction row + outbox inserts.
3. **More processes per host**: one Bun process uses one core; run several replicas per machine (or separate API and consumer/worker processes) instead of 3 on a 12-core box.
4. **Hot wallets**: if a single wallet needs more than ~30 tx/s, move to the conditional atomic update (`UPDATE wallets SET balance = balance - $1 WHERE id = $2 AND balance >= $1`) to shorten the critical section, as discussed in ARCHITECTURE.md.
5. **Measure on separate machines** (load generator, app, database) before drawing capacity conclusions.
